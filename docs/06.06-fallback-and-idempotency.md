## Fallback Patterns

When a service call fails, **fallback** provides an alternative response instead of propagating the error.

### Fallback Strategies

| Strategy | Description | Example |
|:---------|:------------|:--------|
| **Default value** | Return a sensible constant | Empty list, default price |
| **Cached response** | Return last known good value | Cached product details |
| **Degraded mode** | Return partial data | Order without live pricing |
| **Stub response** | Hardcoded response | "Service unavailable" message |
| **Alternative service** | Call backup service | Secondary payment provider |

## Fallback Implementation

### Resilience4j Fallback

```java
@Service
public class RecommendationService {
    
    @CircuitBreaker(name = "recommendations", fallbackMethod = "fallbackRecommendations")
    @Retry(name = "recommendations", fallbackMethod = "fallbackRecommendations")
    public List<Product> getRecommendations(String userId) {
        return recommendationClient.getPersonalized(userId);
    }
    
    // Fallback method - must have same return type
    private List<Product> fallbackRecommendations(String userId, Exception e) {
        log.warn("Recommendations unavailable for {}: {}", userId, e.getMessage());
        
        // Return cached popular products
        return cache.get("popular-products", () -> 
            productService.getPopular(10)
        );
    }
}
```

### Fallback Chain

```java
@CircuitBreaker(name = "primary", fallbackMethod = "trySecondary")
public PaymentResult charge(Order order) {
    return primaryPaymentProvider.charge(order);
}

private PaymentResult trySecondary(Order order, Exception e) {
    log.warn("Primary payment failed, trying secondary: {}", e.getMessage());
    try {
        return secondaryPaymentProvider.charge(order);
    } catch (Exception e2) {
        return queueForLater(order, e2);
    }
}

private PaymentResult queueForLater(Order order, Exception e) {
    paymentQueue.enqueue(order);
    return PaymentResult.pending("Queued for processing");
}
```

```java
            product.setReviews(getReviews(productId));
        }

    }
```

## Idempotency

An **idempotent** operation produces the same result whether called once or multiple times.

### Why Idempotency Matters

```mermaid
sequenceDiagram
    participant C as Client
    participant S as Server
    participant DB as Database
    
    C->>S: POST /payments (charge $100)
    S->>DB: INSERT payment
    S--xC: Response lost (network error)
    Note over C: Did it work?
    C->>S: POST /payments (retry)
    S->>DB: INSERT payment (DUPLICATE!)
```

With idempotency key:

```mermaid
sequenceDiagram
    participant C as Client
    participant S as Server
    participant DB as Database
    
    C->>S: POST /payments, Idempotency-Key: abc123
    S->>DB: INSERT payment (key: abc123)
    S--xC: Response lost
    C->>S: POST /payments, Idempotency-Key: abc123 (retry)
    S->>DB: SELECT WHERE key = abc123
    S->>C: Return cached result
```

## Implementing Idempotency

### Idempotency Key Pattern

```java
@RestController
public class PaymentController {
    
    private final IdempotencyStore idempotencyStore;
    
    @PostMapping("/payments")
    public ResponseEntity<PaymentResult> createPayment(
            @RequestHeader("Idempotency-Key") String idempotencyKey,
            @RequestBody PaymentRequest request) {
        
        // Check for existing result
        Optional<PaymentResult> existing = idempotencyStore.get(idempotencyKey);
        if (existing.isPresent()) {
            return ResponseEntity.ok(existing.get());
        }
        
        // Process new payment
        PaymentResult result = paymentService.charge(request);
        
        // Store result
        idempotencyStore.put(idempotencyKey, result, Duration.ofHours(24));
        
        return ResponseEntity.status(HttpStatus.CREATED).body(result);
    }
}
```

### Idempotency Store

```java
@Component
public class RedisIdempotencyStore implements IdempotencyStore {
    
    private final RedisTemplate<String, String> redis;
    
    @Override
    public Optional<PaymentResult> get(String key) {
        String json = redis.opsForValue().get("idempotency:" + key);
        return Optional.ofNullable(json)
            .map(j -> objectMapper.readValue(j, PaymentResult.class));
    }
    
    @Override
    public void put(String key, PaymentResult result, Duration ttl) {
        redis.opsForValue().set(
            "idempotency:" + key,
            objectMapper.writeValueAsString(result),
            ttl
        );
    }
}
```

### Database-Level Idempotency

```sql
-- Use unique constraint on idempotency key
```

## Idempotent by Design

Some operations are naturally idempotent:

| Method | Idempotent? | Notes |
|:-------|:------------|:------|
| **GET** | Yes | Read-only |
| **PUT** | Yes | Same resource state |
| **DELETE** | Yes | Resource stays deleted |
| **POST (create)** | No | Creates new each time |
| **PATCH** | Depends | Some patches are, some aren't |

### Making POST Idempotent

```java
// Non-idempotent: creates new each time
POST /orders
{"items": [...]}

// Idempotent with client-generated ID
PUT /orders/client-generated-uuid
{"items": [...]}

// Idempotent with idempotency key
POST /orders
Idempotency-Key: unique-key
{"items": [...]}
```

## Handling In-Progress Requests

What if a retry arrives while the first request is still processing?

```java
public PaymentResult processWithLock(String idempotencyKey, PaymentRequest request) {
    // Try to acquire lock
    boolean locked = lockService.tryLock(idempotencyKey, Duration.ofMinutes(5));
    
    if (!locked) {
        // Another request is processing
        throw new ConflictException("Request in progress");
    }
    
    try {
        // Check if already completed
        Optional<PaymentResult> existing = idempotencyStore.get(idempotencyKey);
        if (existing.isPresent()) {
            return existing.get();
        }
        
        // Process
        PaymentResult result = paymentService.charge(request);
        idempotencyStore.put(idempotencyKey, result);
        return result;
        
    } finally {
        lockService.unlock(idempotencyKey);
    }
}
```

## Idempotency Key Best Practices

| Practice | Rationale |
|:---------|:----------|
| **Client generates key** | Client controls retry behavior |
| **UUID format** | Globally unique |
| **Include in request** | Server doesn't guess |
| **TTL for storage** | Clean up old keys |
| **Return cached response** | Same response for same key |

### Key Generation

```javascript
// Client generates key
const idempotencyKey = `order-${orderId}-${Date.now()}-${uuid()}`;

fetch('/api/payments', {
    method: 'POST',
    headers: {
        'Idempotency-Key': idempotencyKey
    },
    body: JSON.stringify(paymentData)
});
```

## Combining Fallback and Idempotency

```java
@CircuitBreaker(name = "payment", fallbackMethod = "paymentFallback")
@Retry(name = "payment")
public PaymentResult charge(String idempotencyKey, Order order) {
    return paymentClient.charge(idempotencyKey, order);
}

private PaymentResult paymentFallback(String idempotencyKey, Order order, Exception e) {
    // Queue for later - include idempotency key
    paymentQueue.enqueue(new QueuedPayment(idempotencyKey, order));
    return PaymentResult.pending("Payment queued");
}

// Background processor uses same idempotency key
@Scheduled(fixedDelay = 5000)
public void processQueue() {
    QueuedPayment queued = paymentQueue.poll();
    if (queued != null) {
        // Retry with same idempotency key - safe even if original succeeded
        paymentClient.charge(queued.getIdempotencyKey(), queued.getOrder());
    }
}
```

??? question "When should you use fallback vs let the error propagate?"
    Use **fallback** when: (1) The feature is non-critical. (2) A degraded response is better than error. (3) You have meaningful cached/default data. **Propagate error** when: (1) The operation is critical (payment). (2) No sensible fallback exists. (3) User should know about failure.

??? question "How long should you store idempotency keys?"
    Balance between: (1) **Long enough** for retry windows (24h is common). (2) **Short enough** to not exhaust storage. Consider: client retry behavior, operation type (payments may need longer), storage costs. 24–72 hours is typical for payment APIs.

??? question "What happens if idempotency store fails?"
    Options: (1) **Fail closed** — reject request (safest for money). (2) **Fail open** — process without check (risk duplicates). (3) **Circuit breaker** — fallback to in-memory or database check. For financial operations, fail closed is usually right.

## 📝 Knowledge Check

<quiz>
A 'personalized prices' call fails. Rank these fallbacks and justify: (a) last-known cached price, (b) list price, (c) empty price field, (d) error page.
- [ ] All equal — anything beats an error
- [x] Depends on business semantics: (b) list price is safe if 'base price' is acceptable for degraded mode; (a) stale personalized price risks quoting expired discounts (fine for display, dangerous at charge time); (c) breaks the UI; (d) loses the sale. The right answer is decided with the business — 'what's the cost of showing wrong-but-plausible vs. showing nothing?'
- [ ] Cached is always best
- [ ] Error page is most honest — always use it

fallback selection is a business decision disguised as a technical one. The killer question: 'is a wrong answer worse than no answer?' For display prices, stale beats absent; for the *charge* path, a wrong price is a real billing error — the transaction must fail honestly. Fallbacks must be scoped per usage site, not per endpoint.
</quiz>
<quiz>
Design a fallback chain for product images: live service → ? → ? → ?
- [ ] Error immediately — images are critical
- [x] Live service → Redis/local cache (last good) → static default/placeholder → omit the module gracefully. Chain rule: each fallback is *less accurate but more available* — and each fallback level should be logged/metered so 'degraded mode' is visible in dashboards, not silent
- [ ] Live → retry forever
- [ ] Live → random product image

fallback chains walk a degradation ladder: freshest-but-fragile down to stale-but-certain. Two requirements: (1) never let a fallback hide the primary's failure from observability — metric every fallback hit, alert on sustained fallback rates; (2) know when to STOP degrading — a chain that ends in a plausible-but-wrong answer is worse than one that ends honestly.
</quiz>
<quiz>
`Idempotency-Key` on POST: what does the server store, and what must it check on a replay?
- [ ] Just the key
- [x] Store key → (request hash, result/status). On replay: same key + same payload → return the stored result (don't re-execute); same key + *different* payload → reject (409/422) — the key means 'this exact operation,' a different body is a protocol violation or a collision; and the check must be atomic with execution so concurrent retries can't double-execute
- [ ] Server checks nothing — key implies trust
- [ ] Store only for GETs

the semantics are 'idempotent operation identity,' not 'cache key': store enough to detect both legit replays (return stored result) and misuse (same key, different body = client bug or key reuse). Atomicity of 'check-and-execute' is where naive implementations break — two parallel retries both miss the check and both charge the card. Lock or unique-constrain on the key.
</quiz>
<quiz>
First request is still *in progress* when the retry arrives with the same key. What are the options?
- [ ] Execute it again — faster is better
- [x] (1) Block-wait on the in-flight operation and return its result when done (best UX, needs a wait/lock mechanism); (2) return `409 Conflict`/`425 Too Early` — 'operation in progress' (simple, pushes work to the client's next retry). Never execute twice — that's the entire point of the key
- [ ] Return 500 — ambiguous state
- [ ] Queue the retry for next hour

'in-progress' is the case simple key-stores forget: the key exists, the result doesn't yet. A short wait (or 'still processing' + Retry-After) beats double-execution; a 409 is honest and simple. What you can't do is let both run — the check-then-act on the key must be atomic through the operation's lifecycle, not just its completion.
</quiz>
<quiz>
Which operations are idempotent 'by design' vs. need keys: PUT, DELETE, POST, conditional update?
- [ ] All need keys
- [x] PUT (replace at known URI — replay = same final state) and DELETE (deleting twice = same 'gone') are naturally idempotent; conditional updates ('set status=shipped where status=paid') self-guard. POST creates new state each call — inherently non-idempotent, hence the key mechanism; you can also *make* it idempotent with client-supplied IDs (upsert semantics)
- [ ] None are idempotent
- [ ] Only GET is idempotent

natural idempotency comes from 'same effect no matter how many times': PUT replaces, DELETE removes, conditional writes no-op on second application. POST's 'create a thing' has no such property — retries mint duplicates. Two production fixes: client-generated idempotency keys, or client-supplied resource IDs making creation an upsert ('create-or-return order #abc').
</quiz>
