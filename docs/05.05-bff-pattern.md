## What is BFF?

**Backend for Frontend** is a pattern where each client type gets its own dedicated backend API layer. Each BFF is tailored to its client's specific needs.

```mermaid
graph TD
    M[Mobile App] --> MBFF[Mobile BFF]
    W[Web App] --> WBFF[Web BFF]
    P[Partner API] --> PBFF[Partner BFF]
    MBFF --> OS[Order Service]
    WBFF --> OS
    PBFF --> OS
    MBFF --> US[User Service]
    WBFF --> US
    WBFF --> RS[Recommendation Service]
```

---

## Why BFF?

### The Problem with Single API

One generic API serving all clients leads to:

| Problem | Impact |
|:--------|:-------|
| **Over-fetching** | Mobile downloads data it doesn't need |
| **Under-fetching** | Web makes multiple calls for one view |
| **Conflicting requirements** | Mobile needs compact, web needs rich |
| **Versioning complexity** | Breaking change affects all clients |
| **Slow iteration** | Backend changes need coordination |

### BFF Solution

Each client gets an optimized API:

| Client | BFF Optimization |
|:-------|:-----------------|
| **Mobile** | Compact payloads, minimal calls, offline support |
| **Web** | Rich data, aggregated views, real-time updates |
| **Partner** | Stable contract, full documentation, rate limits |
| **Smart TV** | Paginated lists, image URLs, simple auth |

---

## BFF Responsibilities

| Responsibility | Description |
|:---------------|:------------|
| **Aggregation** | Combine data from multiple services |
| **Transformation** | Shape responses for client needs |
| **Protocol translation** | REST for mobile, GraphQL for web |
| **Client-specific auth** | Different auth flows per client |
| **Caching** | Cache strategies per client pattern |
| **Error handling** | Client-appropriate error messages |

## BFF Implementation

### Mobile BFF Example

```java
@RestController
@RequestMapping("/api/v1/dashboard")
public class MobileDashboardController {
    
    private final OrderClient orderClient;
    private final UserClient userClient;
    
    @GetMapping
    public MobileDashboardResponse getDashboard(@RequestHeader("X-User-Id") String userId) {
        // Parallel calls
        CompletableFuture<List<Order>> ordersFuture = 
            CompletableFuture.supplyAsync(() -> orderClient.getRecentOrders(userId, 5));
        CompletableFuture<User> userFuture = 
            CompletableFuture.supplyAsync(() -> userClient.getUser(userId));
        
        // Wait and combine
        List<Order> orders = ordersFuture.join();
        User user = userFuture.join();
        
        // Transform for mobile — compact payload
        return MobileDashboardResponse.builder()
            .userName(user.getFirstName())
            .orderCount(orders.size())
            .orders(orders.stream()
                .map(o -> MobileOrderSummary.builder()
                    .id(o.getId())
                    .status(o.getStatus())
                    .total(o.getTotal())
                    .build())
                .toList())
            .build();
    }
}
```

### Web BFF Example

```java
@RestController
@RequestMapping("/api/v1/dashboard")
public class WebDashboardController {
    
    @GetMapping
    public WebDashboardResponse getDashboard(@RequestHeader("X-User-Id") String userId) {
        // More data for web
        CompletableFuture<List<Order>> ordersFuture = 
            CompletableFuture.supplyAsync(() -> orderClient.getOrders(userId, 20));
        CompletableFuture<User> userFuture = 
            CompletableFuture.supplyAsync(() -> userClient.getUserWithPreferences(userId));
        CompletableFuture<List<Product>> recommendationsFuture = 
            CompletableFuture.supplyAsync(() -> recommendationClient.getForUser(userId));
        
        // Rich response for web
        return WebDashboardResponse.builder()
            .user(userFuture.join())  // Full user object
            .orders(ordersFuture.join().stream()
                .map(this::toDetailedOrder)  // Includes items, addresses
                .toList())
            .recommendations(recommendationsFuture.join())
            .analytics(getAnalytics(userId))
            .build();
    }
}
```

## BFF Ownership

| Model | Description | Trade-offs |
|:------|:------------|:-----------|
| **Frontend team owns BFF** | Mobile team owns Mobile BFF | Best alignment; may lack backend skills |
| **Fullstack team** | Team owns client + BFF | Fast iteration; team size grows |
| **Dedicated BFF team** | Central team manages all BFFs | Consistency; becomes bottleneck |
| **Platform team + contracts** | Platform provides framework; teams extend | Balance of control and flexibility |

!!! tip "Frontend team ownership preferred"
    The team building the client understands its needs best. They should control the BFF to iterate quickly.

---

## BFF vs API Gateway vs GraphQL

| Aspect | API Gateway | BFF | GraphQL |
|:-------|:------------|:----|:--------|
| **Purpose** | Cross-cutting concerns | Client-specific API | Flexible queries |
| **Aggregation** | Limited | Yes, per client | Yes, per query |
| **Transformation** | Basic | Full control | Client specifies |
| **Ownership** | Platform team | Frontend team | Backend team |
| **Complexity** | Low | Medium | Medium |
| **Use case** | Auth, rate limiting | Client optimization | Multiple clients, flexible |

### When to Use Each

| Scenario | Solution |
|:---------|:---------|
| **Centralized auth, rate limiting** | API Gateway |
| **Multiple clients, different needs** | BFF per client |
| **Flexible queries, one backend** | GraphQL |
| **All of the above** | Gateway → BFF → Services |

---

## BFF Anti-Patterns

| Anti-Pattern | Problem | Fix |
|:-------------|:--------|:----|
| **BFF with business logic** | Duplicates service logic | Keep business logic in services |
| **BFF calling BFF** | Complexity explosion | BFFs call services only |
| **Shared BFF for all clients** | Back to generic API problem | One BFF per client type |
| **BFF as data cache** | Stale data, consistency issues | Cache at edge or service level |
| **Too many BFFs** | Maintenance burden | Consolidate similar clients |

## BFF with Service Mesh

In a service mesh, BFFs are just services. They get the same benefits:

```mermaid
graph TD
    subgraph Edge
        GW[API Gateway]
    end
    subgraph Mesh
        MBFF[Mobile BFF + Envoy]
        OS[Order Service + Envoy]
        US[User Service + Envoy]
    end
    GW --> MBFF
    MBFF --> OS
    MBFF --> US
```

BFF sidecars handle mTLS, retries, and observability automatically.

### Contract Testing

```java
@Pact(consumer = "mobile-bff", provider = "order-service")
public RequestResponsePact getOrdersPact(PactDslWithProvider builder) {
    return builder
        .given("orders exist for user 123")
        .uponReceiving("a request for recent orders")
        .path("/orders")
        .query("userId=123&limit=5")
        .method("GET")
        .willRespondWith()
        .status(200)
        .body(newJsonArrayMinLike(1, order -> 
            order.stringType("id")
                 .stringType("status")))
        .toPact();
}
```

??? question "When should you use BFF vs a single API Gateway?"
    Use BFF when clients have **significantly different needs**: different data shapes, different aggregation, different auth flows. Use single gateway when clients are similar or the team doesn't want to maintain multiple services. Consider GraphQL as a middle ground — one backend, flexible queries.

??? question "Should the frontend team or backend team own the BFF?"
    **Frontend team** is generally preferred. They understand client needs best and can iterate quickly. However, they need backend skills (API design, service integration). A compromise: platform team provides a BFF framework; frontend teams extend it.

??? question "How do you avoid duplicating logic across multiple BFFs?"
    (1) **Keep business logic in services** — BFFs only aggregate and transform. (2) **Shared libraries** for common transformation logic. (3) **GraphQL** as a single flexible BFF. (4) Accept some duplication — it's the cost of client optimization.

## 📝 Knowledge Check

<quiz>
When does adding a BFF actually *remove* complexity instead of adding a layer?
- [ ] Always — decoupling is always good
- [x] When client-specific shaping would otherwise contaminate shared services: without a BFF, the Order API grows `?mobile=true` branches and returns 40 fields for 3-field clients; the BFF absorbs per-client divergence, leaving domain services generic. With ONE client, the BFF is pure overhead
- [ ] When clients share identical needs
- [ ] When the gateway is slow

BFF pays when divergence is real: mobile vs. web vs. partner needing different payloads, aggregations, or auth contexts. It converts 'every service serves N client dialects' into 'each client team owns its adapter.' The failure mode is BFF-for-one-client — a pass-through layer adding a hop, a deploy, and a failure point for zero divergence.
</quiz>
<quiz>
Who should own the mobile BFF — and why does ownership matter more than the code?
- [ ] The platform team — it's infrastructure
- [x] The mobile/frontend team: the BFF is 'the backend shaped like my client' — when the client team owns it, they iterate their API surface without cross-team PRs; platform ownership recreates the ticket queue the BFF was meant to eliminate
- [ ] The backend team — they know the services
- [ ] Rotating ownership quarterly

BFF is an *organizational* pattern disguised as a technical one: its entire value is decoupling client iteration speed from backend release cycles. Client-owned BFF = the team closest to the need shapes the contract. If the platform/backend team owns it, you've built an API gateway with extra steps — same bottleneck, more layers.
</quiz>
<quiz>
A BFF starts accumulating 'small rules' — 'if user is premium, include pricing tier X.' What's the failure mode?
- [ ] Nothing — BFFs can hold logic
- [x] Business logic migration: pricing rules in the mobile BFF diverge from the web BFF and bypass domain invariants — now two client adapters make business decisions the domain service should own. BFFs transform, aggregate, and trim; business decisions stay in domain services
- [ ] It's fine until there are 3 BFFs
- [ ] Move it to the gateway instead

the BFF gravity well: every 'just this once' business rule makes the BFF smarter and the domain dumber, and rules fork per client ('mobile premium means X, web premium means Y'). The test: does the rule express a *domain* invariant (applies to all clients) or a *presentation* choice (this screen only)? Domain rules belong downstream of the BFF.
</quiz>
<quiz>
BFF vs GraphQL gateway — when is each the right answer to 'clients need different data shapes'?
- [ ] They're mutually exclusive — pick one philosophy
- [x] GraphQL solves shape-divergence with a query language (one layer, client-defined fields — good when divergence is mostly 'which fields'); per-client BFFs solve it with owned code (good when clients differ in *behavior* — auth flows, orchestration, protocols, caching — not just fields). Many systems combine them (GraphQL BFF per client type)
- [ ] GraphQL replaces BFFs entirely
- [ ] BFF is only for mobile

'which fields' is a query problem (GraphQL's sweet spot); 'which workflow' is an ownership problem (BFF's sweet spot). If mobile needs a different auth handshake, different aggregation pattern, and offline sync semantics — that's per-client *logic*, better in its own codebase than in resolver complexity. Field-subsetting alone doesn't justify N BFFs.
</quiz>
<quiz>
Your BFF fans out to 8 backend services per screen. What resilience controls are mandatory?
- [ ] None — it's just aggregation
- [x] Per-call timeouts, parallel calls (not serial), per-dependency circuit breakers, and graceful degradation: a BFF's P99 is the slowest of 8 calls and its availability is the product of them — the response model must support partial data ('recommendations failed → render page without that module'), not all-or-nothing
- [ ] Increase the BFF's timeout to cover the slowest service
- [ ] Make calls serial for simplicity

BFFs multiply tail latency by design: serial fan-out sums latencies; parallel takes the max — plus whichever dependency is having a bad day. Design every widget as 'nice-to-have vs must-have': must-haves failing = 5xx; nice-to-haves failing = render without them + track degraded responses in metrics so 'partial' isn't invisible.
</quiz>
