## What is an API Gateway?

An **API Gateway** is a single entry point for all client requests. It handles cross-cutting concerns and routes requests to backend services.

```mermaid
graph TD
    M[Mobile] --> GW[API Gateway]
    W[Web] --> GW
    P[Partner] --> GW
    GW --> O[Order Service]
    GW --> U[User Service]
    GW --> PAY[Payment Service]
```

---

## Core Responsibilities

| Responsibility | Description |
|:---------------|:------------|
| **Routing** | Direct requests to appropriate backend services |
| **Authentication** | Validate JWT/API keys before forwarding |
| **Authorization** | Check permissions for routes |
| **Rate Limiting** | Throttle per client/IP |
| **SSL Termination** | Handle TLS; internal traffic can be plain HTTP |
| **Load Balancing** | Distribute across service instances |
| **Caching** | Cache GET responses |
| **Request/Response Transform** | Modify headers, body shape |
| **Aggregation** | Combine multiple service responses |
| **Observability** | Centralized logging and metrics |

## Routing Patterns

### Path-Based Routing

```yaml
routes:
  - path: /api/orders/**
    service: order-service
  - path: /api/users/**
    service: user-service
  - path: /api/products/**
    service: product-service
```

### Header-Based Routing

```yaml
routes:
  - headers:
      X-API-Version: v2
    service: order-service-v2
  - headers:
      X-API-Version: v1
    service: order-service-v1
```

### Canary Routing

```yaml
routes:
  - path: /api/orders/**
    targets:
      - service: order-service-v1
        weight: 90
      - service: order-service-v2
        weight: 10
```

## Authentication at the Gateway

Validate tokens centrally; forward validated claims to services.

```mermaid
sequenceDiagram
    participant C as Client
    participant GW as API Gateway
    participant AS as Auth Server
    participant S as Service
    
    C->>GW: Request + JWT
    GW->>GW: Validate JWT signature
    GW->>GW: Check expiry, issuer, audience
    alt Invalid
        GW->>C: 401 Unauthorized
    else Valid
        GW->>S: Request + X-User-Id header
        S->>GW: Response
        GW->>C: Response
    end
```

### Gateway JWT Configuration (Kong)

```yaml
plugins:
  - name: jwt
    config:
      claims_to_verify:
        - exp
      key_claim_name: kid
      secret_is_base64: false
  - name: request-transformer
    config:
      add:
        headers:
          - X-User-Id:$(jwt.claims.sub)
```

## Rate Limiting

Protect backend services from overload.

### Rate Limiting Strategies

| Strategy | Description |
|:---------|:------------|
| **Per client** | Limit by API key or user ID |
| **Per IP** | Limit by source IP |
| **Per route** | Different limits per endpoint |
| **Global** | Total gateway throughput |

### Rate Limiting Response

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1699900000
```

### Configuration (Kong)

```yaml
plugins:
  - name: rate-limiting
    config:
      minute: 100
      hour: 1000
      policy: redis
      redis_host: redis
```

## Request/Response Transformation

Modify requests before forwarding or responses before returning.

### Use Cases

| Transformation | Example |
|:---------------|:--------|
| **Add headers** | Add correlation ID, user context |
| **Remove headers** | Strip internal headers from response |
| **Rename fields** | Map external field names to internal |
| **Filter response** | Remove sensitive fields |

### Example (Kong)

```yaml
plugins:
  - name: request-transformer
    config:
      add:
        headers:
          - X-Request-ID:$(uuid)
          - X-Forwarded-Host:$(host)
      remove:
        headers:
          - X-Internal-Header
```

## Response Caching

Cache GET responses to reduce backend load.

```yaml
plugins:
  - name: proxy-cache
    config:
      strategy: memory
      content_type:
        - application/json
      cache_ttl: 300
      cache_control: true
```

### Cache Considerations

| Consideration | Recommendation |
|:--------------|:---------------|
| **TTL** | Short for dynamic data; longer for static |
| **Invalidation** | Use cache headers or explicit purge |
| **Vary headers** | Cache per user if response varies |
| **Storage** | Redis for distributed; memory for single instance |

## Gateway Aggregation

Combine responses from multiple services into one response.

```mermaid
sequenceDiagram
    participant C as Client
    participant GW as API Gateway
    participant OS as Order Service
    participant US as User Service
    participant PS as Product Service
    
    C->>GW: GET /dashboard
    par Parallel
        GW->>OS: GET /orders
        GW->>US: GET /profile
        GW->>PS: GET /recommendations
    end
    OS->>GW: Orders
    US->>GW: Profile
    PS->>GW: Recommendations
    GW->>GW: Aggregate
    GW->>C: Combined dashboard
```

### Aggregation Trade-offs

| Benefit | Cost |
|:--------|:-----|
| Single client request | Gateway complexity |
| Reduced latency (parallel calls) | Partial failure handling |
| Tailored response | Business logic at gateway edge |

## Gateway Deployment Patterns

### Single Gateway

```mermaid
graph TD
    C[Clients] --> GW[API Gateway]
    GW --> S1[Service 1]
    GW --> S2[Service 2]
    GW --> S3[Service 3]
```

Simple; single point of failure.

### Regional Gateways

```mermaid
graph TD
    subgraph US Region
        C1[Clients] --> GW1[Gateway US]
    end
    subgraph EU Region
        C2[Clients] --> GW2[Gateway EU]
    end
    GW1 --> Services
    GW2 --> Services
```

Lower latency; regional compliance.

### Gateway per Domain

```mermaid
graph TD
    C[Clients] --> R[Router/LB]
    R --> GW1[Orders Gateway]
    R --> GW2[Users Gateway]
    R --> GW3[Products Gateway]
    GW1 --> OS[Order Services]
    GW2 --> US[User Services]
    GW3 --> PS[Product Services]
```

Domain team ownership; avoid monolithic gateway.

---

## Anti-Patterns

| Anti-Pattern | Problem | Fix |
|:-------------|:--------|:----|
| **Business logic in gateway** | Gateway becomes monolith | Keep gateway thin |
| **Coupling to implementation** | Changes require gateway changes | Route by contract, not implementation |
| **No rate limiting** | DoS vulnerability | Always configure limits |
| **No timeout** | Stuck connections | Set upstream timeouts |
| **Monolithic gateway config** | Hard to manage | Modular configs per team |

## Gateway vs Service Mesh

| Aspect | API Gateway | Service Mesh |
|:-------|:------------|:-------------|
| **Traffic type** | North-south (external → cluster) | East-west (service → service) |
| **Deployment** | Edge of cluster | Sidecar per pod |
| **Scope** | External API concerns | Internal communication |
| **Examples** | Kong, AWS API Gateway | Istio, Linkerd |

Often used together: Gateway at edge, mesh for internal.

---

??? question "When should you use an API Gateway vs direct service calls?"
    Use a gateway when: (1) You need centralized auth, rate limiting, or logging. (2) Multiple clients with different needs. (3) You want to decouple clients from backend topology. Direct calls are fine for internal service-to-service (use service mesh instead).

??? question "How do you prevent the API Gateway from becoming a monolith?"
    (1) Keep business logic in services, not gateway. (2) Use gateway only for cross-cutting concerns. (3) Consider BFF pattern — gateway per client type. (4) Modular config — each team manages their routes. (5) Avoid aggregation that requires domain knowledge.

??? question "What happens when the API Gateway fails?"
    The gateway is a single point of failure. Mitigations: (1) High availability — multiple instances behind load balancer. (2) Health checks — remove unhealthy instances. (3) Circuit breaker — fail fast if backend down. (4) Regional failover — route to another region. (5) Client retry — with backoff.

## 📝 Knowledge Check

<quiz>
The gateway validates JWTs at the edge. Should services still verify tokens?
- [ ] No — that's double work
- [x] Yes — defense in depth: the gateway check is your perimeter, but services must not trust 'the gateway already checked' — a misrouted request, a compromised internal hop, or a direct service call bypasses it. Verify signature/claims (or enforce mTLS identity) at the service too; gateway auth is a convenience layer, not the trust boundary
- [ ] Only for external calls
- [ ] Only if using zero-trust marketing slides

'the gateway checked it' is a perimeter assumption — and the whole point of zero-trust is perimeters leak. Service-side verification (JWT signature + audience/scope checks, or mesh mTLS identity) costs little and removes the single point of total bypass. Edge validation remains useful for cheap early rejection and rate-limit keying.
</quiz>
<quiz>
Canary routing at the gateway: `/orders` gets `90% → v1, 10% → v2`. What must be true for this to give a *safe* signal?
- [ ] Nothing — just split traffic
- [x] You need observability per version (error rate/latency tagged by version, not blended), automated rollback criteria, and session-affinity decisions (or you get users flapping between versions mid-flow). Also: the 10% must be representative — internal-only or 'beta opt-in' cohorts bias the signal
- [ ] Canary only works with feature flags
- [ ] Split 50/50 for a fair test

weighted routing is easy; the discipline is measurement: metrics/logs/traces must label version so you compare v2 against v1's baseline, not against nothing. Automate the verdict (error-rate or latency regression → route 0% to v2). And mind user-level consistency for stateful flows — header/cookie-based stickiness if version-skew mid-session breaks things.
</quiz>
<quiz>
Rate limiting at the gateway returns `429`. What should the response include and what distinguishes it from a 503?
- [ ] Just the code — semantics are clear
- [x] Include `Retry-After` and rate-limit headers (`X-RateLimit-Limit/Remaining/Reset`) so clients can back off correctly. 429 = 'YOU exceeded YOUR quota' (client-specific, retry later per policy); 503 = 'the SYSTEM is overloaded' (global, maybe shed load) — they need different client behavior and different alerting
- [ ] They're interchangeable
- [ ] 429 means the service is down

429 tells a well-behaved client exactly when to come back; a bare 429 without `Retry-After` invites retry storms. 503+Retry-After says the service itself is shedding load — useful with circuit breakers upstream. Clients should treat them differently: 429 = self-throttle to quota; 503 = exponential backoff and consider the endpoint degraded.
</quiz>
<quiz>
A team plans response caching at the gateway for `GET /products`. What decides if it's safe?
- [ ] Cache everything — it's read-only
- [x] Personalization and staleness: public catalog data = safe with TTL; anything user-specific (prices by account tier, stock by region) must be keyed correctly or skipped — a cache miss-leak of user A's data to user B is a security incident, not a bug. Respect `Cache-Control`, vary by auth context, and plan invalidation on product updates
- [ ] Only cache POST responses
- [ ] Cache headers don't matter at the gateway

edge caching is free latency *until* it's personalized. The rules: cache only shared/public representations, key the cache on everything that changes the response (tenant, tier, locale), honor the origin's cache directives, and have an invalidation story (event or short TTL) for updates. Personalization bugs at the edge are cross-tenant leaks — the worst kind.
</quiz>
<quiz>
Single gateway vs gateway-per-domain vs regional gateways — what drives the choice?
- [ ] Always single — simpler
- [x] Blast radius + ownership + latency: one gateway is a single failure domain and a config-contention point for all teams; per-domain gateways let teams own their edge policy and fail independently; regional gateways cut cross-region latency and contain regional outages — at the cost of multiplied config and policy-drift management
- [ ] More gateways = faster
- [ ] Gateways can't be regional

the gateway is on every request's path, so its failure domain = your availability floor. A single shared gateway concentrates both outages and change conflicts; per-domain/regional splits trade ops overhead for isolation and locality. The anti-pattern to avoid either way: gateway config becoming a shared file every team edits.
</quiz>
